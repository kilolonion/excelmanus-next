# 17 技能与模型指导内容的开发约束

本规范约束内置任务技能、工具说明和产品帮助的新增与修改。2026-10-01 按用户要求调整职责，决策见 [ADR 0016](decisions/0016-task-skills-and-guidance-boundaries.md)。定位与权限是【硬性】；编写结构为【推荐】，不按篇幅、文件数或技能数验收。

## 1. 什么是 skill

Skill 是按需加载、可复用的任务方法包：名称和描述用于发现，正文提供判断与方法，参考资料/模板/脚本按任务需要读取。SKILL.md 是入口而非软件手册；只有入口文件也可以构成完整技能。

参考 [Agent Skills 定义](https://agentskills.io/home)、[格式规范](https://agentskills.io/specification) 和 [编写实践](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)。这些说明解释格式；本项目的运行方式与安全边界以 docs/ 为准。格式合法不证明内容有效。

## 2. 职责归属【硬性】

| 内容 | 唯一维护位置 | 不得放入技能充当基础用法 |
| --- | --- | --- |
| 身份、通用行动原则、权限原则 | kernel 系统提示词；运行时执行权限 | 单个业务流程与工具参数 |
| 工具参数、结果、错误、角色、执行限制、SDK/发布语义 | 工具定义的 description/input/output，相关实现与契约文档 | 让模型先加载某技能才知道如何正确调用工具 |
| 功能介绍、设置位置、操作入口、形态限制 | [用户帮助](user-guide.md)，设置与引导 UI；动态能力以实际工具与结果为准 | 手写一份完整的静态能力目录作为 skill |
| 某类任务的判断、方法、交付标准、非显然陷阱 | assets/skills/<name>/SKILL.md 与其资源 | 重复基础工具契约或扩大用户范围 |
| 用户的长期要求/业务口径 | 规则或记忆，按用户授权管理 | 把某次示例或作者偏好变成通用技能规则 |

删除、备份、冲突、审批、沙箱限制由运行时保证。禁用全部技能后，工具应仍可正确使用，安全保护仍成立。加载技能不授予权限、不增加工具、不执行附带文件。

技能可以提到合适的工具，以及选择某种方法的理由；参数格式和设施语义必须查工具说明。SDK 最小例子若必须随方法出现，应与真实边界测试共用契约并保持验证，不能复制独立的 SDK 手册。

## 3. 新增技能前的判断【硬性】

提交者需在变更说明/验收记录回答：

1. 用户要完成什么独立任务，具体交付物是什么？
2. 哪些非显然知识会改变模型的决策？是否已在工具说明中提供？
3. 为什么需要独立技能，而不是补充现有技能的一个参考章节？
4. 适用范围、可替代路线和完成标准是什么？
5. 哪个真实输入与结果检查能证明价值？

仅有“先读再写”“调用某工具”“设置在这里”、参数清单或系统限制的内容不能新增为内置技能。不得按功能按钮、工具 mode 或软件模块机械拆技能。没有实质增量的短文本应删除或归位；也不得为了显得完整填充常识或强行合并独立任务。

## 4. 编写与资源【推荐】

- description 写任务和触发条件，避免“任何表格问题都使用”式兜底。简单单次操作可直接用工具，运行时不要求所有相关任务加载技能。
- 正文包含目标、影响结论的判断、可选执行路线、完成核验及交付边界。结构按实际任务调整，不靠固定标题或字数识别质量。
- 用户明确的范围、模板、输出位置和算法优先。只有影响正确性且不能从现有信息确定的问题才需询问；不新增重复审批。
- 有多个合理方法时解释选择条件。SQL、公式、脚本、团队都是可选手段；不得因某次样例成功而强制所有任务走同一路径。
- 业务默认值必须有依据并说明适用范围。例如对账容差、日期顺序、去重键、币种、单位不能由作者随意固定。
- 大量情境实例放 references/，入口说明何时读取，引用用技能根的相对路径。不要让细小参考章节成为新技能；不要默认加载全部资源。
- scripts/ 只在确实减少重复实现时添加；只能通过当前 QuickJS 与受控 SDK 使用，导入不意味着允许宿主 shell/Python。新增脚本必须真实执行验证。
- 当前内置技能保留七个任务边界，不设数量目标；清单见 [12 §1.6](12-skills-memory-mcp.md#16-v1-内置技能推荐)。

## 5. 格式与加载【硬性】

- name 为不超过 64 字符的 kebab-case，与目录名一致；description 非空且不超过 1024 字符，内置索引描述按 12 §1.2 控制在 100 字以内；正文非空。
- 内置技能显式声明 requires-tools，只列任务必需工具。有替代方法的路线用本项目扩展 optional-tools 声明可选工具，并说明不可用时的替代方法，不把 agent_spawn 等设施误设为整个任务的硬依赖。内置技能的必需/可选工具名都须通过目录检查。
- 社区格式的 requires-tools 可缺省；缺省不代表引用不存在的产品工具也可用。必需依赖及正文/Markdown 参考资料中未声明为可选的可识别工具引用按实时目录校验；缺失时标不可用，显式调用也拒绝。资源检测限制与 read 一致，仅检查清单中不超过 1 MiB 的 Markdown；更大的技术资料需拆成任务需要的参考文件。
- 编写时工具名用反引号标注。自动识别仅覆盖反引号中的已知名称与 workbook_/agent_/run_/ask_/mcp_ 前缀；普通文字、自定义外部工具名和业务含义仍需人工审阅。它不是语义分类器，也不是完整静态分析。
- 来源覆盖仍按内置 < 用户 < 工作区整体覆盖；不能因清理内置技能而删除用户/工作区中的同名目录或历史日志。旧会话系统提示词保持冻结，下一次环境说明更新索引。
- 不伪造已退役技能的别名；用户自己安装的同名技能仍按普通来源规则处理。未知斜杠前缀继续按普通文本处理。

## 6. 验证与证据【硬性】

| 验证 | 能证明 | 不能证明 |
| --- | --- | --- |
| 格式、资源路径、工具引用门禁 | 包能解析、资源可读取、依赖可定位 | 方法正确、业务结果改善 |
| 真实 HTTP/WS/SQLite + 假模型 | 索引、加载、注入、错误、日志/投影可重建 | 模型会选对技能或按技能完成任务 |
| 真实模型任务评测 | 对实际输入的输出质量、调用与成本变化 | 未运行模型或未测场景的泛化效果 |

每个内置技能至少一个任务评测场景，覆盖其关键判断与交付核验。使用隔离数据目录，对照启用/禁用技能的同一输入、模型和指令；记录模型、输入/技能版本、成功率、工具次数、token、耗时及失败类别。输出检查以值/结构/对象断言为主；视觉类任务还需实际图像对照。评测输入与检查见 [技能评测说明](skill-evals.md)。

修改内容后按 [14 §6](14-quality.md#6-真实模型评测) 重跑三类模型。没有模型或凭据时，提交实现与可执行场景并明确“真实模型效果未验证”；不能用假模型或格式测试补写通过。

内容语义由评审检查，不通过禁词、固定段落、最小字数或固定数量伪装成质量门禁。历史验收保留原环境与结果，新验收说明变化与未通过项。

## 7. 开发收口清单

检查 docs/12、docs/04、工具定义、技能目录与索引、设置帮助、桌面打包资源是否一致；同步新清单但不改写历史验收数量。运行相关真实边界测试、资源门禁、类型检查和项目要求的门禁。不得读取生产密钥或发送用户文件做评测；使用独立配置与合成样例。
