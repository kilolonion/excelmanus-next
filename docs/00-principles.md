# 00 重写原则

## 1. 为什么重写

旧项目经历了"Python 后端 → Node/TypeScript + fork 上游 pi 内核"的迁移，迁移只完成了一半。2026-09-27 的审计记录了 74 条问题，其中 24 条为 P0。问题的根源不在某个模块，而在结构：

| 旧项目的结构性问题 | 表现 | 新项目的对策 |
| --- | --- | --- |
| 前后端各有一套字段命名，中间没有共享契约 | 后端发 `textDelta`、前端读 `content`，助手回复整段消失；`isError` 被读成 `success:undefined`，成功的写入显示为失败 | 一个契约包同时生成服务端校验与前端类型，字段只定义一次（见 [11](11-api-contract.md)） |
| fork 了上游 agent 框架再大量改造 | 框架的宿主层能力（压缩、扩展点）在绕开的路径上丢失，只能补丁式追加 | 不 fork 任何框架。提供商适配用成熟库，agent 循环是产品自己的小而清楚的代码（见 [03](03-architecture.md)、[04](04-agent-runtime.md)） |
| 运行状态只在内存里 | 重启后待审批消失、会话卡死 | 会话的每个状态变化先写入会话日志，再推送给前端；重启后从日志恢复（见 [10](10-data.md)） |
| 验证手段本身不可信 | 覆盖率脚本报"0 缺口"实际 84 个；冒烟测试在仓库内能过、装到用户机器上起不来；"跨重启"测试其实在同一进程里模拟 | 测试少而真实：跑真实 HTTP、同步通道和 SQLite，假模型只替代模型输出（见 [14](14-quality.md)） |
| 工具多、能力发现难 | 一次回归分析任务调用 58 次工具，55% 用在确认"我有没有写工具" | 工具少而完整，任何时刻模型看到的工具清单就是它能用的全部；不做"按需发现工具"（见 [06](06-tools.md)） |
| 技能、工具说明、知识门户、提示词分层互相重叠 | 同一条规则写在四处，改了一处其他处过期；技能引用不存在的工具 | 三层严格分工，自动检查技能引用的工具是否存在（见 [04 §7](04-agent-runtime.md#7-提示词分层)） |
| 文档声称与实现脱节 | "已完成"表格大量失实 | 文档只写设计；进度与缺口只记在 [backlog](backlog.md)，不在多处重复声明完成状态 |
| 承诺过多 | 修订历史、撤销、合并审阅、自助升级等功能半实现或返回 501 | v1 只承诺做得到的；做不到的明确不做 |

## 2. 不可违背的原则【硬性】

### 2.1 事实优先于叙述

- 用户看到的"完成了什么"必须来自系统记录的真实结果，而不是模型的自述。每轮结束时，界面根据实际发生的文件变更生成**变更摘要**（改了哪些文件、哪些工作表、多少单元格、新增了哪些图表），与模型回复并列展示。模型说"已添加图表"但实际没有图表时，用户一眼能看出来。
- 工具返回的状态必须区分：已完成、未执行、已执行但结果不确定、失败。不能把"没执行"报成"失败"诱导重试，也不能把"失败"报成"成功"。
- "不支持"就明确说不支持，不返回空列表或假成功。

### 2.2 单一事实源

每一类事实只在一个地方定义，其他地方从它生成或引用：

| 事实 | 唯一来源 | 派生物 |
| --- | --- | --- |
| REST、同步通道消息、会话日志记录类型 | 契约包中的 schema | 服务端校验、前端类型、接口文档 |
| 工具参数与说明 | 工具定义（schema + 说明文字放在同一处） | 发给模型的工具列表、前端工具卡片的参数展示、测试 |
| 工具是否写入、是否需要审批 | 工具定义中的副作用声明 | 审批策略、审计记录、子代理权限裁剪 |
| 会话状态 | 会话日志 | 投影（模型上下文、界面时间线、待处理交互…）、同步通道续传、重启恢复 |
| 工作簿内容 | 活文档的文档日志（xlsx 为检查点） | 工作台、代理读取、截图、变更摘要 |
| 设置项 | 设置 schema | 设置页表单、校验、默认值、搜索 |

### 2.3 用户文件安全

- 模型不能在用户不知情的情况下破坏用户原始文件。修改用户已有文件前，系统强制先留一份备份（机制见 [07 §7](07-workbook-engine.md#7-修改前备份)）。
- 写入必须带上"我读到的是哪个修订、哪些区域"。读过的区域在读取后被别人（用户在界面上编辑、另一个代理、外部程序）改过，重叠区域的写入被拒绝，要求重新读取（区域级语义见 [03 §6.1](03-architecture.md#61-文档内)）。
- 删除文件、调用外部服务等不可逆操作必须经过审批，除非用户显式开启了相应的自动批准。

### 2.4 可恢复性

- 进程崩溃或重启后：已持久化的对话、待审批请求、排队消息、子代理状态都能恢复；运行到一半的步骤标记为"中断"，**不自动重放有副作用的操作**，由用户决定是否继续。
- 浏览器刷新、网络断开后，前端能通过同步通道续传，不丢失、不重复。

## 3. 工程原则【推荐】

1. **少即是多**。能用一个通用机制解决的，不做三个专用机制。例如：子代理之间的消息、用户在运行中追加的消息、审批结果，都走同一个"会话收件箱"。
2. **边界清楚胜过功能多**。每个模块回答"我负责什么、我不负责什么"。
3. **先打通端到端，再扩展**。第一个里程碑就要跑通"用户发消息 → 模型读表 → 改表 → 前端看到变更"，而不是先把某一层做完美。
4. **依赖成熟组件，但隔离它们**。第三方库放在适配层后面（模型网关、表格编解码、沙箱），替换时不波及业务代码。
5. **不为兼容而兼容**。新项目没有旧数据、没有旧客户端，不写任何兼容分支。
6. **可观测**。每个请求、每轮对话、每次工具调用都有 ID，日志能串起来；日志不记录密钥、文件内容和提示词正文。
7. **测试少而真实**。测试替身只替代模型输出，不替代我们自己的代码；真实模型的效果靠实际试用，不用假模型测试冒充（见 [14](14-quality.md)）。

## 4. 实现者的工作方式【推荐】

- 功能优先：先把用户能用的功能做出来，再在容易出错的地方补测试；不为"完整"堆测试、验收记录或防御代码。
- 遇到文档没有覆盖的问题，按最接近的原则自行判断并实现；影响较大或拿不准的，记到 [backlog](backlog.md) 或在提交说明里写清楚。
- 不要复制旧仓库代码。旧仓库可以作为"用户期望的行为"参考去操作体验，但其实现不作参考。
