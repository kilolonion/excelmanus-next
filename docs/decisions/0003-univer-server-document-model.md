# 0003 服务端活文档采用 Univer 无头实例 + mutation 转发（带传输修补与对账点）

- 状态：已接受
- 日期：2026-09-29

## 背景

07 §2.1【推荐，需 M0 验证】：服务端用 Univer 无头实例作为活文档的内存模型，文档操作即 Univer mutation。07 §12 通过标准：20 万行 × 30 列载入 ≤ 3 s、小提交 p99 ≤ 20 ms、内存 ≤ 1.5 GB、1,000 个随机操作序列回放一致。07 §3.3、§7.4–7.5、03 §6.3 另需要"每个修订的逆操作"。

证据：`spikes/univer-model/REPORT.md`（A1）、`REPORT-A1b.md`（A1b）及 `results/`。`@univerjs/* 1.0.2` 精确锁定（发布未满 7 天，A1 中已注明原因）；无 DOM polyfill，`UniverSheetsNodeCorePreset` 在纯 Node 可用。

| 项 | 实测 | 判定 |
| --- | --- | --- |
| 载入 20 万 × 30（600 万格） | p50 1,268 ms；RSS p50 1,462 MB | 通过（内存贴线） |
| 单元格写 p99 | 0.09 ms | 通过 |
| 插/删单行 | 50k×20 ≈ 77 ms；200k×30 ≈ 417 ms（与位置无关） | 参考 |
| 1,000 序列回放一致 | 原始 908/1000；加两条传输修补后 **1000/1000** | 通过（有条件） |
| 内置 undo 回滚 | 53% | 不可用 |
| 写集前像逆操作 | 逐操作 99.3%；序列 80%；排除 remove-sheet/move-range 后 100% | 部分可用 |
| 快照重建回滚 | 50k×20 ≈ 0.6 s；200k×30 ≈ 3.6 s | 兜底可用 |
| 分叉实例 dryRun | 50k 约 0.36 s，200k 约 2.1 s，结果 100/100 一致；连续分叉后 RSS 残留 | 可用但有内存疑点 |

## 选项

### 选项 A：mutation 转发 + 传输修补 + 对账点（采用）

前端产生的 mutation 原样发给服务端，服务端 `executeCommand(id, params, { fromCollab: true })` 复现；在传输层按 mutation id 应用修补规则。

### 选项 B：命令转发（服务端重放用户命令）

A1b 实测命令重放不等价：同一序列多出 1,725 处差异（命令的范围/选区解析依赖客户端上下文）。排除。

### 选项 C：07 §2.2 备选（自有稀疏模型）

性能与一致性已达标，无需切换。

## 决定

选 A。具体约定：

1. **传输修补**（在 `modules/workbook` 的传输层，规则按 mutation id 登记，未登记的 id 原样转发）：
   - `R-styles-subset`：`sheet.mutation.insert-sheet` 补充 `params.styles`，内容为新表引用到的样式子集（copy-sheet 在 1.0.2 丢样式表）。
   - `R-filter-reconcile`：每次提交后比较发送方与服务端的 `SHEET_FILTER_PLUGIN` 资源（ref、filterColumns、cachedFilteredOut），有漂移就合成一条 `sheet.mutation.set-filter-range` 追加到本修订。根因是筛选的"自动扩张"是监听器副作用，mutation 流里没有。
   - 对账点做成通用机制，资源清单逐项列出；以后发现其他监听器型副作用插件，按同一模式加对账项，并补回放测试。
   - 禁止使用 `onlyLocal` 作为复现选项（会同时抑制正常写入，实测 1,664 处差异）。
2. **快照定影**：任何 `createWorkbook(snapshot)` 调用前先深拷贝快照（Univer 不拷贝传入对象，后续 mutation 会污染调用方持有的快照）。
3. **逆操作（07 §3.3、§7.4、§7.5、03 §6.3）不使用 Univer 的 UndoRedoService**（私有 API，覆盖率 53%）。改为由写集推导前像：
   - 每个修订用写集（A1 T4 的 37 条规则，自检违例 0）保存受影响区域的前像，结构操作用成对的逆操作；这是"修改前的值"（§7.4）的来源。
   - 修订中含 `remove-sheet` 或 `move-range` 时，该修订**不生成逆操作**，标记为"需快照回滚"。需要回退时（仅跨文档批次失败时，03 §6.3），从最近的文档快照 + 文档日志重建到目标修订。
   - 逆操作仍只作内部机制，不开放给用户（附录 C P-9 不变）。
4. **dryRun（07 §3.3）**：同一写集前像 + 逆操作实现"应用 → 读取结果 → 回退"，不用分叉实例；遇到上一条的"需快照回滚"操作，dryRun 只返回写集与预览数据，不实际应用。分叉实例方案不采用：内存会翻倍，且连续分叉后有未定性的 RSS 残留。
5. **容量**：
   - 活文档非空单元格上限从 500 万改为 **400 万**。实测每百万单元格约 175 MB，600 万格时 RSS 已贴近 1.5 GB，公式和对象层还要留余量。
   - 超过上限的工作簿走只读大文件模式（07 §6.4）。
   - 单个文档 worker 的内存预算按"每百万格约 200 MB"估算。
6. **结构操作成本**：大表单行插删约 0.4 s，而且与位置无关。批量结构编辑必须合并为一次提交；工具说明提示代理一次插删多行。
7. **回放一致性门禁**（14 §2"Univer 操作回放一致性测试"）直接复用 spike 的随机序列生成器、严格比较器和修补规则，进入 `modules/workbook` 的测试。CI 每次提交抽样 100 序列；Univer 升级时跑满 1,000 序列。

## 后果

- 正面：一个模型同时服务工作台、代理读取、公式和截图（07 §2.1 的收益成立）；提交延迟有约 200 倍余量。
- 负面 / 代价：
  - 传输修补与对账点跟 Univer 内部行为耦合，每次升级都要重跑回放测试并复核规则（附录 C T-12）。
  - remove-sheet / move-range 的回退要走快照重建，大表约需 3.6 s。
  - 400 万格上限比原设更保守。
- 需要跟进的事项：
  - M1 实现只读文档 actor 时，接入快照定影与写集推导；M2 实现修补规则、对账点、前像逆操作与门禁。
  - 同步修改 07 §3.3（逆操作来源）、§11（活文档上限）；附录 C T-11 以本 ADR 关闭。
  - T-12（升级兼容策略）保留：文档日志记录 `engine_version`，升级时回放旧日志。

## 验收标准符合性

- 07 §12 "Univer 作为服务端模型"：载入、延迟、内存、1,000 序列回放四项在带修补的条件下全部满足（A1b 1c：1000/1000，0 失败）。
- 14 §2 "Univer 操作回放一致性测试"：由第 7 条落地为 CI 门禁。
- 活文档硬性约束（单一写入者、修订严格递增、日志先落库）不受影响：修补与对账点在同一修订内完成。
