# ADR 0017：流式对话滚动归属与历史阅读位置

- 日期：2026-10-01
- 状态：采纳（用户指定流式滚动修复）

## 背景

对话面板每次 React 渲染无条件 `scrollIntoView`，流式增量、输入草稿和其他会话状态变化均可将用户拉回底部；该 API 还可能滚动祖先容器。原 02 §3.1 没有定义阅读历史与跟随生成如何切换。用户本次明确要求区分两者，补充到 02 §3.1，不增加会话状态或变更历史。

## 选项

1. 仅按当前距底部判断是否跟随：内容增长会使原本跟随的视口脱离底部，内容收缩又会误恢复；无法稳定区分用户意图。
2. 所有滚动均暂停跟随、只能按钮恢复：会把程序自己的滚动误认为用户操作，且滚回底部仍需额外操作。
3. 显式跟随状态 + 同步用户输入释放 + 视口滚动/布局观测 + 消息锚点：程序写入与浏览器范围校正不改变跟随状态，主动返回底部或按钮恢复。

## 决定

采用选项 3，交互规则以 02 §3.1 为准。单个滚动控制器拥有对话视口的写入；以 ref 中同步状态取消已排队的自动滚动，React 状态仅用于恢复按钮。ResizeObserver 负责异步布局变化，requestAnimationFrame 合并更新。自由阅读关闭浏览器滚动锚定，保存可见块标识与偏移，由同一控制器恢复，避免双重校正。缓存保留当时已应用的日志游标，回放未追上时不接受临时短内容触发的顶部校正；已追上且内容变短时按有效范围裁剪，避免永久等待。工具详情复用可聚焦的 ScrollArea，使用 overscroll containment，并隔离键盘导航。

不引入依赖、不引入虚拟列表或改变日志/同步契约。最近视图位置是有限的页面内存偏好，不持久化消息正文。发送与生成结束不自动抢回滚动权。

## 后果与验收

用户选择文字或操作历史详情后需主动返回底部或使用恢复按钮继续跟随。消息锚点被替换或删除时退回原 scrollTop 并按有效范围裁剪；不承诺保持被删除内容的阅读位置。刷新默认跟随，缓存超过 30 个视图会淘汰最旧项。

验收使用生产 Web 构建 + 真实 HTTP/WS/SQLite + 延迟假模型：向上滚动/键盘/触摸与拖动滚动条、持续生成中稳定阅读、底部附近释放、显式恢复、停止/消息落定、展开思考、缩放、输入、切换与面板重挂载。专项证据见 [流式滚动验收](../acceptance/chat-scroll-2026-10-01.md)。
